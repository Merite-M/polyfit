## 2026-11-12 - Employee Portal OTP Authentication Bypass and Credential Leakage
**Vulnerability:** Universal demo OTP bypass codes (`123456`, `000000`) were accepted in production environments without checking `NODE_ENV !== 'production'`. Additionally, `demo_otp` was disclosed in HTTP response payloads for Rwandan mobile numbers (`788`, `789`) and corporate domains (`bk.rw`), verification codes were compared using vulnerable non-constant-time equality (`===`), and lack of attempt bounding permitted brute-force enumeration.
**Learning:** Development test shortcuts using broad substring heuristics (such as matching telco prefix `788` or corporate domain `bk.rw`) accidentally matched legitimate production users, leaking credentials. Bypasses must never rely on data values and must be strictly gated by `process.env.NODE_ENV !== 'production'`. Verification codes also require attempt bounding and constant-time comparison to thwart brute-force and timing attacks.
**Prevention:** Strictly enforce `process.env.NODE_ENV !== 'production'` on all test bypasses and debug payload fields, bound cache verification attempts to 5 with HTTP 429 lockout, and compare all secrets/OTPs using `safeCompare`.

## 2026-11-05 - Timing Side-Channel Vulnerability in Secret Comparisons
**Vulnerability:** Comparing sensitive authentication tokens and keys (such as `CRON_SECRET`, `TURNSTILE_API_KEY`, and dynamic pass signatures) using standard string equality operators (`===` and `!==`) exposed endpoints to timing side-channel attacks.
**Learning:** V8 and JavaScript string comparisons short-circuit upon the first mismatched character, causing response latency to vary depending on matching characters. Direct usage of `crypto.timingSafeEqual` throws `RangeError` if input buffer lengths differ, which can leak secret length or crash endpoints. Pre-hashing both inputs with SHA-256 guarantees equal 32-byte buffers and ensures true constant-time comparison without length leakage.
**Prevention:** Always use `safeCompare` from `@polyfit/shared-utils` for comparing secret keys, API tokens, webhook secrets, and signatures instead of standard equality operators.

## 2025-05-18 - PostgREST Filter Injection in Supabase .or() Queries
**Vulnerability:** User-supplied search/filter strings interpolated directly into Supabase PostgREST `.or(...)` query strings allowed PostgREST filter injection via structural syntax control characters (`,`, `(`, `)`).
**Learning:** Supabase PostgREST parses string arguments passed to `.or()` using specific structural delimiters (where `,` separates clauses and `()` groups logic). Unsanitized user inputs containing these characters alter query syntax or inject arbitrary conditions.
**Prevention:** Always sanitize user inputs before passing them into Supabase `.or()` strings by stripping structural delimiters (`() , : . % _` and quotes) using `sanitizePostgrestFilter`.

## 2026-03-30 - Open Redirect and Auth Token Exfiltration in Auth Workflows
**Vulnerability:** In `/api/auth/magic-link` and `/api/auth/password-reset`, user-controlled `redirectTo` query/body parameters were passed directly to Supabase Auth (`emailRedirectTo` / `redirectTo`), enabling attackers to craft authentication or password-reset requests that redirect authenticated users and sensitive OTP/reset tokens to attacker-controlled origins.
**Learning:** External authentication helpers often delegate URL dispatching to the configured callback parameter. Without strict origin validation, attackers can exploit open redirects to harvest magic-link session tokens or password reset tickets. Additionally, naive relative path checks can be bypassed using protocol-relative (`//evil.com`) or Windows backslash (`/\\evil.com`) URI schemas.
**Prevention:** Always sanitize and validate redirect URLs against whitelisted frontend origins and permit relative paths only when verifying they do not start with `//` or `/\\`. Fall back to configured safe default URLs (`FRONTEND_URL`) when unrecognized destinations are supplied.
